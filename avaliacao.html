8,0 PONTOS 1. Ingestão de Dados máx 1,6 pts
Três simuladores geram eventos IoT em tempo real: GPS dos ônibus (300 veículos/ciclo, pool configurável de 850, bounding box de Brasília), Catracas do VLT (18 estações, eventos ENTRY/EXIT, LGPD: card_id nunca persiste — apenas SHA-256+salt em card_hash), e Bikes (30 estações de bicicleta compartilhada). O banco PostgreSQL legado fornece 5.000 viagens sintéticas (30 dias) extraídas via task Airflow. Cada simulador publica JSON imutável no MinIO Bronze com fallback automático para escrita local.
→ simulador_gps.py → simulador_catracas.py → simulador_bikes.py → init_postgres.sql
simulador_gps.py — função geradora de evento linha ~35
def gerar_evento_gps(vehicle_id: str, line_id: str, ts: datetime) -> dict: speed = round(random.gauss(35, 15), 1) speed = max(0.0, min(speed, 90.0)) is_outlier = random.random() < 0.005 # 0.5% de outliers → quarentena if is_outlier: speed = round(random.uniform(100, 140), 1) return { "vehicle_id": vehicle_id, "line_id": line_id, "direction": random.choice(["IDA", "VOLTA"]), "lat": round(random.uniform(LAT_MIN, LAT_MAX), 6), # bbox Brasília "speed_kmh": speed, "occupancy_pct": random.randint(0, 100), "status": random.choices(STATUS, STATUS_PESOS)[0], "timestamp": ts.isoformat(), "schema_version": "1.1", }

GPS — ônibus

  • 300 veículos/ciclo (pool: 850)
  • 120 linhas simuladas (L001–L120)
  • Bounding box: Brasília (-15.95/-15.55, -48.30/-47.75)
  • Velocidade: gauss(35, 15) km/h · outlier: > 120 km/h
  • Status: on_route 75% · at_stop 15% · delayed 8% · out 2%
  • Partição: ano/mes/dia/hora

Catracas VLT + LGPD

  • 18 estações (EST-01 a EST-18)
  • Eventos: ENTRY / EXIT
  • Cartões: SINGLE, MONTHLY, STUDENT, SENIOR

  • Bikes: 30 estações, bikes_available + docks_available
  • Postgres: 5.000 viagens · 30 dias sintéticos
8,0 PONTOS 2. Armazenamento — Data Lake Medallion máx 1,6 pts
Armazenamento em padrão Medallion com três camadas de qualidade crescente. Bronze: MinIO (S3-compatível) com JSON imutável — dados originais nunca sobrescritos, particionados por ano/mes/dia/hora para auditoria total. Silver: Parquet comprimido com Snappy após ETL pandas. Gold: DuckDB com tabelas analíticas. Quarentena: registros inválidos isolados com coluna _motivo_rejeicao para reprocessamento. Toda a infraestrutura sobe com docker compose up -d em ~3 minutos.

8,0 PONTOS 3. Transformação — Bronze → Silver → Gold máx 1,6 pts
Bronze → Silver (bronze_to_silver.py): pipeline pandas com deduplicação por chave composta, remoção de nulos obrigatórios, normalização de timestamps UTC, sinalização de outliers (is_outlier=True — não deleta, preserva auditabilidade), validação de coordenadas e enriquecimento com dimensão de veículos. Registros inválidos vão para quarentena com motivo de rejeição.

Silver → Gold (dbt_project/): 5 modelos dbt (staging, intermediate, marts) com 28 testes de qualidade automáticos (not_null, unique, accepted_values) executados a cada ciclo. Falha em qualquer teste bloqueia a escrita no Gold.
→ bronze_to_silver.py → dbt schema.yml (28 testes) → dbt models/

# Simuladores em paralelo → Bronze → ETL → dbt run → dbt test → notificação [sim_gps, sim_catracas, sim_bikes, batch_pg] >> b2s >> dbt_run >> dbt_test >> notifica # Configurações do DAG schedule_interval = "0 * * * *" # a cada hora retries = 2 retry_exponential_backoff = True catchup = False max_active_runs = 1 # Variáveis configuráveis no UI do Airflow (sem alterar código) n_veic = int(Variable.get("gps_veiculos_por_ciclo", default_var=300)) n_evt = int(Variable.get("catracas_eventos_por_ciclo", default_var=200)) # XCom — métricas passadas entre tasks context["ti"].xcom_push(key="gps_count", value=len(eventos)) context["ti"].xcom_push(key="silver_metricas", value=json.dumps(metricas))

Configurações da DAG

  • Airflow 2.9 (Docker)
  • Schedule: 0 * * * * (a cada hora)
  • Retries: 2 com backoff exponencial
  • Catchup: False (não re-executa passado)
  • Max active runs: 1 (sem sobreposição)

Funcionalidades avançadas

  • Parallelism: 4 tasks de ingestão simultâneas
  • XCom: métricas de qualidade entre tasks
  • Variáveis configuráveis no UI
  • Fallback local se MinIO indisponível
  • trigger_rule=all_done na notificação

serving/main.py — endpoint /kpis/operacional (SQL dinâmico sobre Parquet) ~linha 80
@app.get("/kpis/operacional", tags=["KPIs"]) def kpis_operacional(line_id: Optional[str] = Query(None), limit: int = Query(100)): silver_path = str(SILVER_DIR / "gps_onibus_clean/**/*.parquet") sql = f""" WITH base AS ( SELECT line_id, direction, speed_kmh::DOUBLE, CASE WHEN speed_kmh::DOUBLE > 120 THEN TRUE ELSE FALSE END AS is_outlier, CASE WHEN status = 'on_route' THEN 1 ELSE 0 END AS em_rota FROM read_parquet('{silver_path}') ), agg AS ( SELECT line_id, direction, ROUND(AVG(speed_kmh), 2) AS velocidade_media_kmh, ROUND(100.0 * SUM(em_rota) / NULLIF(COUNT(*), 0), 1) AS otp_pct FROM base GROUP BY line_id, direction ) SELECT *, CASE WHEN otp_pct >= 90 THEN 'VERDE' WHEN otp_pct >= 70 THEN 'AMARELO' ELSE 'VERMELHO' END AS semaforo_otp FROM agg ORDER BY otp_pct DESC LIMIT {limit} """ return _query(sql) # DuckDB lê Parquet diretamente — sem ORM, sem servidor SQL

2,0 PONTOS 7. README com Change Log — Relatório de Mudanças máx 1,0 pt
README completo com instruções de execução (2 opções: POC local e Docker completo), estrutura do repositório, stack tecnológica, e Relatório de Mudanças Parte 1 → Parte 2 documentando cada desvio do plano original com justificativa técnica.
→ README.md completo → README.md → seção "Relatório de Mudanças"

1. Apache Superset → FastAPI

Superset requer ~1,5 GB de RAM adicionais e inicialização de ~5 minutos para criar usuários e importar dashboards. FastAPI entrega o mesmo valor de POC com documentação automática (Swagger) e latência < 50ms.

Justificativa: restrição de recursos no ambiente de desenvolvimento.

2. Simulador de Bikes implementado (estava só planejado na Parte 1)

simulador_bikes.py implementado com 30 estações, status de disponibilidade e integração ao pipeline Bronze→Silver e à DAG. Completa os três modais do problema de negócio (ônibus, VLT, bikes).

Justificativa: necessário para demonstrar o valor completo do projeto.

3. Quarentena adicionada (ausente na Parte 1)

Registros que falham validação são gravados em quarentena/ com coluna _motivo_rejeicao. Garante auditabilidade e possibilidade de reprocessamento — em vez de descartar silenciosamente.

4. dbt com 28 testes (vs. 26 planejados)

Dois testes adicionais necessários após identificar valores inesperados em semaforo_otp e periodo_dia durante validação inicial. Ambos usam accepted_values.

5. Extração Postgres integrada à DAG principal

Task batch_postgres integrada à DAG urbanflow_pipeline (em vez de DAG separada). Dados legados e IoT seguem o mesmo ciclo de transformação, simplificando operação e monitoramento.
